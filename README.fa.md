# rmtunnel

**ساخته‌ی [Ali Rahmani](https://github.com/Ali-Rahmanii) — تلگرام: [@A_Alirahmani](https://t.me/A_Alirahmani)**

یک تانل معکوس (reverse tunnel) سبک و یکپارچه: فورواردینگ **TCP و UDP** روی
ترنسپورت **TCP/TCPMux**، سه روش استتار اتصال (`plain` / `noise` / `wss`) با
سوییچ خودکار بینشون، پشتیبانی از مسیر **Direct** (وقتی پورت ورودی ایران رد
نمی‌شه)، یکپارچه‌سازی با تانل خارجی **[paqet](https://github.com/hanselime/paqet)**
(پروتکل خام روی پکت + KCP، برای عبور از فایروال‌های سخت‌گیر)، مدیریت چندتانلی،
و یک بنچمارک داخلی که کانفیگ رو دقیقاً بر اساس سخت‌افزار و لینک واقعی خودت
تنظیم می‌کنه.

مستندات کامل انگلیسی: [README.md](README.md). این فایل خلاصه‌ی فارسیه —
برای جزییات فنی هر بخش (فرمت دقیق کانفیگ، پروتکل، و غیره) به همون فایل مراجعه کن.

## معماری، خیلی خلاصه

```
  کاربر ──▶ سرور (ایران) ══ تانل (plain/noise/wss یا paqet) ══▶ کلاینت (خارج) ──▶ سرویس واقعی
            پورت عمومی رو باز می‌کنه                                    وصل میشه به سرور          (مقصد توی کانفیگ سرور)
```

- **سرور (Iran)**: پورت‌هایی که کاربر نهایی بهشون وصل میشه رو باز می‌کنه (`[[ports]]`).
- **کلاینت (Kharej)**: جایی که سرویس واقعی (X-UI، پنل، WireGuard، ...) اجرا میشه یا بهش دسترسی داره.

### Reverse در مقابل Direct

- **Reverse (پیش‌فرض)**: کلاینت (خارج) به سرور (ایران) وصل میشه — همون روال معمول.
- **Direct**: برعکس — سرور (ایران) به کلاینت (خارج) وصل میشه. از این حالت وقتی
  استفاده کن که پورت ورودی ایران رد نمیشه ولی خروجیش سالمه. توجه: تو هر دو حالت،
  **ایران همیشه پورت‌ها رو برای کاربر باز می‌کنه** — فقط جهت شروع اتصال عوض میشه.

> ⚠️ **نکته‌ی مهم درباره‌ی ترتیب راه‌اندازی**: هر طرفی که در اون جهت «گوش میده»
> (Listen) باید **اول** ساخته و اجرا بشه، وگرنه طرف دیگه چیزی برای وصل شدن پیدا
> نمی‌کنه:
> - **Reverse**: اول **ایران** (سرور)، بعد **خارج** (کلاینت).
> - **Direct**: اول **خارج** (کلاینت)، بعد **ایران** (سرور).
>
> خود منو در همون لحظه که جهت رو انتخاب می‌کنی این ترتیب رو بهت یادآوری می‌کنه.

## اجرا کردن

راه ساده — منوی رنگی و تعاملی:

```bash
sudo rmtunnel
```

نصب روی سرور:

```bash
curl -fsSL https://raw.githubusercontent.com/Ali-Rahmanii/rmtunnel/main/install.sh | sudo bash
```

منوی اصلی:

```
1) Build Iran tunnel (server)     — ساخت تانل سمت ایران
2) Build Kharej tunnel (client)   — ساخت تانل سمت خارج
3) Manage tunnels                 — مدیریت تانل‌های موجود
4) Tune server (OS optimization)  — بهینه‌سازی کرنل/شبکه
5) Speed & hardware benchmark     — بنچمارک سرعت و سخت‌افزار
6) Update script                  — بروزرسانی اسکریپت
7) Uninstall                      — حذف کامل
H) Help                           — راهنمای گام‌به‌گام هر نوع تانل
0) Exit
```

ویزارد ساخت تانل (گزینه‌ی ۱ یا ۲) این سوالات رو به ترتیب می‌پرسه:

1. **جهت** (Reverse یا Direct)
2. اسم تانل (یه سرور می‌تونه چندتا تانل همزمان اجرا کنه)
3. توکن امنیتی (خالی بذاری خودش می‌سازه)
4. **ترنسپورت**: TCP یا TCP Mux (چندین جلسه روی چندتا کانکشن — برای بار همزمان بالا بهتره)
5. اگه جهت Direct باشه: **موتور** — `rmtunnel` (پیش‌فرض، همین کد خودش) یا **paqet** (پایین‌تر توضیح داده شده)
6. کدوم روش‌های استتار فعال باشن (`wss`/`noise`/`plain`) — پیشنهاد: هر سه، خودش سوییچ می‌کنه — و برای سمتی که وصل میشه (نه گوش میده)، **آدرس‌های پشتیبان** اختیاری (اگه آدرس اصلی قطع/بلاک شد، خودش میره سراغ بعدی)
7. (سمت سرور) پورت‌هایی که باید فوروارد بشن — فرمت‌های قابل قبول: `1232`، `1232:2323`، یا `1232=host:2323`، با کاما جدا برای چندتایی، به‌همراه یک سوال درباره‌ی فوروارد UDP هم
8. تنظیم عملکرد: بنچمارک زنده، وارد کردن دستی سرعت/تاخیر لینک، یا انتخاب یه tier آماده (light/medium/heavy/extreme/insane)

بعدش کانفیگ رو می‌سازه و پیشنهاد می‌ده که همون‌جا به‌عنوان سرویس systemd نصب و اجرا بشه.

## paqet — تانل خام روی پکت + KCP

[paqet](https://github.com/hanselime/paqet) یه پروژه‌ی جدا و مستقله (مجوز MIT)
که پکت‌های TCP رو مستقیم می‌سازه و با pcap می‌گیره — بدون رد شدن از استک TCP/IP
خود سیستم‌عامل — و روی این، KCP و smux رو برای یه ترنسپورت سریع، امن، و چندکاناله
سوار می‌کنه. این می‌تونه از فایروال‌هایی که به handshake یا ردیابی کانکشن
(connection tracking) تکیه دارن رد بشه.

**rmtunnel این پروژه رو دوباره‌نویسی نکرده** — چون خودش کامل و تست‌شده‌ست. در
عوض، منوی rmtunnel:

- باینری رسمی paqet رو (برای معماری سیستم خودت) از گیت‌هابش دانلود و نصب می‌کنه
- با یه ویزارد کامل، تمام تنظیمات paqet رو می‌پرسه: اینترفیس شبکه، IP، آدرس MAC
  گیت‌وی (با تلاش برای تشخیص خودکار روی لینوکس)، پورت گوش‌دادن، حالت KCP
  (`normal` / `fast` / `fast2` / `fast3` / `manual`)، و برای حالت manual یه
  پریست **gaming** آماده با بیشترین بهینه‌سازی برای کمترین پینگ
- پورت‌های فوروارد و SOCKS5 (سمت ایران) رو دقیقاً با همون فرمتی که خود
  rmtunnel استفاده می‌کنه می‌پرسه
- قوانین **iptables** (`NOTRACK`) که مستندات خود paqet برای پایداری زیر بار
  واقعی الزامی می‌دونه رو خودش اعمال و پایدار (persist) می‌کنه
- تانل paqet رو به‌عنوان سرویس systemd نصب می‌کنه و توی همون صفحه‌ی
  **Manage tunnels** کنار تانل‌های خود rmtunnel نشون می‌ده (start/stop/restart/logs/delete یکسانه)
- ویرایش بعدی: تغییر پورت‌های فوروارد یا کلید/پریست KCP، از همون منو

**نکته‌ی مهم درباره‌ی نقش‌ها در paqet**: توی خود paqet، نقش «client» یعنی طرفی
که پورت‌ها رو برای کاربر باز می‌کنه (= ایران در اصطلاح rmtunnel) و همین طرف هم
اول شروع به وصل شدن می‌کنه. نقش «server» یعنی طرفی که منتظر میشه و سرویس واقعی
روش اجراست (= خارج). یعنی paqet ذاتاً شکل **Direct** داره — دقیقاً به همین
دلیل زیر گزینه‌ی Direct قرار گرفته.

نیاز به **root** و **libpcap** روی هر دو سرور داره (باینری‌های ریلیز خود
paqet روی لینوکس استاتیک کامپایل شدن، پس نیازی به نصب جداگونه‌ی libpcap نیست).

## پنل مدیریت تانل‌ها (Manage tunnels)

همه‌ی تانل‌های ساخته‌شده روی این سرور (چه rmtunnel چه paqet) توی یه لیست میان:

- **Edit** — تغییر توکن/کلید، پورت‌ها، استتارها یا تنظیمات KCP، یا tier عملکرد
  — هر کدوم اگه نیاز به تغییر مشابه توی سمت مقابل داشته باشه، صریح اعلام میشه
- **Start / Stop / Restart / View logs / Delete**
- **Restart ALL** — همه‌ی تانل‌ها با یه تایید
- **Health Check** — بررسی root/systemd/BBR/qdisc، قدرت توکن هر تانل، بافرهایی
  که از سقف سیستم (`net.core.rmem_max`/`wmem_max`) بیشترن، و تداخل پورت بین
  دو تانل روی یه سرور — هر مورد با یه راه‌حل مشخص
- **File Locations** — مسیر دقیق همه‌ی کانفیگ‌ها، سرویس‌ها و لاگ‌ها

## انتخاب سطح عملکرد (Tier) و بنچمارک

یه اسم tier به‌تنهایی فقط یه حدسه. چیزی که واقعاً روی سرعت واقعی تاثیر می‌ذاره
اینه که بافرها (`recv_buf`/`send_buf`/`mux_stream_buffer`) حداقل به اندازه‌ی
**bandwidth-delay product** لینک (پهنای‌باند × تاخیر رفت‌وبرگشت) باشن — کمتر
از این، سرعت یه اتصال رو محدود می‌کنه، مهم نیست لینک واقعی چقدر سریعه.

```bash
# روی یکی از سرورها:
rmtunnel bench server 0.0.0.0:9999 یک-توکن-موقت
# روی سرور دیگه:
rmtunnel bench client آی‌پی-سرور:9999 یک-توکن-موقت
```

این دستور تاخیر و سرعت واقعی بین دو سرور رو اندازه می‌گیره، CPU/RAM محلی رو
می‌خونه، و یه tier پیشنهادی (light / medium / heavy / extreme / insane) با
مقادیر آماده برای paste کردن چاپ می‌کنه. خود ویزارد ساخت تانل هم می‌تونه
همین اندازه‌گیری رو مستقیم انجام بده — نیازی به کپی دستی عدد نیست.

## چیزهایی که عمداً اینجا نیست

- ترنسپورت خام UDP یا KCP/QUIC **بومی** (native) — به‌جاش paqet برای همین
  سناریو یکپارچه شده؛ ساختن یه موتور کاملاً جدید برای همون هدف، کار تکراری
  بی‌فایده‌ای بود
- تونل کامل Layer-3/IP (مثل GRE-in-Noise بک‌پک) یا bonding چند-سوکته
- ACME/Let's Encrypt خودکار، ربات تلگرام، یا پنل وب — این پروژه عمداً یه
  باینری تک‌فایلی با یه فرمت کانفیگ می‌مونه
- محدودیت پهنای‌باند به‌ازای هر کانکشن

جزییات بیشتر (باگ‌های واقعی پیدا و رفع شده، دلیل هر تصمیم معماری) توی
[docs/TUNING.md](docs/TUNING.md) و [docs/CENSORSHIP.md](docs/CENSORSHIP.md) هست.
